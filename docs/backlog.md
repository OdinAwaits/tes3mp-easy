## BL-001. Кириллица не вводится в клиенте на Linux (Proton/Wine)

**Статус:** отложено (28.10.2026). Обходной путь для игры: латинские логины и
пароли (см. `README.txt` в пакете восстановления).

**Симптом.** В клиенте TES3MP, запущенном на Linux через Proton, невозможно
ввести кириллицу в поля логина/пароля и в чат: нажатия либо не дают символов,
либо подставляются латинские. На Windows и в нативной Linux-сборке TES3MP
ввод работает.

<details>
<summary>Причина, варианты и проверка</summary>

**Причина.** Игра получает текст через `SDL_TEXTINPUT`
(`apps/openmw/mwinput/keyboardmanager.cpp` → `KeyboardManager::textInput` →
MyGUI, Unicode). На Windows текст формирует ОС (`WM_CHAR`), поэтому
раскладка не важна. Под Wine символ рождается из «скан-код → раскладка», а
раскладка берётся из таблиц самого Wine (`winex11.drv`), которые не знают
кириллических групп XKB: в игру приходит пустая строка. Проблема слоя
Wine/X11, а не клиента и не сервера. Пароли сервера к этому не относятся: они
хранятся как `passwordSalt` + `passwordHash` и считаются по цепочке
`sha256(pw)` → `sha256(h + sha256(sha256(h)))` → `sha256(clientHash + salt)`
(`server/scripts/player/base.lua:155-158`, `eventHandler.lua:689`).

**Что известно про варианты (все — Linux-only, Windows не затрагивают):**

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| `PROTON_ENABLE_WAYLAND=1` в env дочернего процесса | одна переменная, без внешних пакетов, не трогает настройки Proton/Steam/префикс | только Wayland-сессия и Proton 9+/GE; на X11 клиент не стартует; нужна проверка, что кириллица действительно появляется |
| gamescope + `XKB_DEFAULT_LAYOUT` / `XKB_DEFAULT_OPTIONS` | работает на X11 и Wayland, предсказуемо: Xwayland gamescope отдаёт двухгрупповую раскладку | нужен пакет `gamescope`; в SteamOS game mode вложенный gamescope конфликтует (`GAMESCOPE_WAYLAND_DISPLAY`); лишний слой вывода; больше кода: поиск бинаря, `-W/-H`, предпросмотр команды |
| `HKCU\Keyboard Layout\Preload` = `00000419,00000409` в нашем префиксе | без внешних пакетов, изолировано в нашем префиксе | хрупко: зависит от сшивки XKB-групп с этим списком в Wine; ошибка «тихо не работает» |
| Нативный клиент `tes3mp-GNU+Linux-x86_64` вместо Proton | убирает причину целиком, ввод через SDL2 X11 работает без env | отдельный архив/имя бинаря/`LD_LIBRARY_PATH`, смена каталога конфигов и сейвов, правки doctor/docs/тестов; сборка 2022 г. на SDL2 2.0.9 |

Проверено фактами: `XKB_*` без gamescope бесполезны (раскладку даёт системный
X/композитор); автоподбор разрешения возможен только на X11 (`xrandr`), на
Wayland аналога нет; `[Video] resolution` в `settings.cfg` — внутреннее
разрешение игры, а не размер вывода gamescope; TES3MP 0.8.1 действительно
публикует Linux-архив с `TES3MP/tes3mp`, `TES3MP/tes3mp.x86_64` и
`TES3MP/lib/*`.

**Как проверять.** На машине с RU-раскладкой: (1) запустить клиент с
`PROTON_ENABLE_WAYLAND=1`, попробовать ввести кириллицу в поле логина;
(2) при провале — то же под `gamescope -f --backend sdl` с
`XKB_DEFAULT_LAYOUT=us,ru` и `XKB_DEFAULT_OPTIONS=grp:alt_space_toggle`;
(3) для варианта с реестром — выставить `Preload` в префиксе и повторить.
Критерий успеха везде один: в поле логина появляются русские буквы.

**Решение, если браться.** Сначала дешёвые проверки (флаг Wayland, затем
реестр), и только при их провале — gamescope или нативный клиент. Любая
реализация — это Linux-only ветка запуска плюс opt-in поле «дополнительные
переменные окружения» в расширенных настройках, с записью итоговой команды в
clientlog.

</details>

## BL-002. Сервер печатает `[ERR]: [Script]: Could not find Lua CJSON!`

**Статус:** отложено (28.10.2026). Сначала замер: на текущих данных выигрыш
измеряется миллисекундами, поэтому правка сейчас даёт тишину в логе, а не
скорость.

**Симптом.** При загрузке скриптов сервер пишет в лог:

```text
[ERR]: [Script]: Could not find Lua CJSON! The decoding and encoding of JSON files will always use dkjson and be slower as a result.
```

Сервер после этого работает штатно.

<details>
<summary>Причина, варианты и проверка</summary>

**Причина.** `server/lib/lua/jsonInterface.lua` сначала проверяет модуль через
`doesModuleExist("cjson")` (`server/lib/lua/utils.lua`, обход
`package.searchers`), и только при успехе берёт `cjson`. В нашем рантайме
`cjson` не находится, поэтому ветка `else` печатает `[ERR]` и весь JSON дальше
идёт через `dkjson`. `require("cjson")` не срабатывает потому, что C-модуль
должен лежать в `package.cpath` встроенного LuaJIT — то есть в
`<runtime>/lib/*.so`; системный `lua-cjson` там не виден. Рантайм ставит
`bootstrap.sh` и он root-owned, поэтому «просто положить файл руками» не
вариант: обновление TES3MP его всё равно перезапишет.

**Кто использует JSON.** Все чтения/записи мира идут через один интерфейс:
`server/scripts/cell/json.lua:49` (загрузка клетки), `player/json.lua:50`,
`recordstore/json.lua:44`, `world/json.lua:26-27`, `serverCore.lua:75,124`
(`banlist.json`). Загрузка клетки: `eventHandler.lua:1261` →
`logicHandler.LoadCell` → `cell/json.lua:49`. Сохранения всегда идут через
`dkjson` (`jsonInterface.save`), `cjson` ускоряет только `quicksave` и `load`.

**Почему это не срочно.** Данные маленькие: 244 файла `world/cell/*.json`,
суммарно ~2.3 МБ, самый большой — 68 КБ. `dkjson` разбирает такой файл за
единицы миллисекунд, а переход между клетками тратит время на I/O, Lua-логику и
сеть. Ускорение от `cjson` тонет в шуме; выгода сейчас — только чище лог.

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Собирать `lua-cjson` в `bootstrap.sh` и класть `.so` в `<runtime>/lib/` | убирает `[ERR]`, ускоряет `load`/`quicksave` | нужен компилятор и заголовки LuaJIT при установке; ручной шаг после каждого обновления TES3MP; артефакт в root-owned рантайме; нужна проверка в `ops doctor`, иначе «тихо не собралось» |
| Гасить сообщение патчем `jsonInterface.lua` при установке | одна строка, без зависимостей | патчим чужой рантайм при каждом обновлении; скорость не меняется |
| Ничего не делать | ноль работы и риска | `[ERR]` в логе путает оператора и маскирует настоящие ошибки скриптов |

**Как проверять.** На сервере с реальным миром измерить `logicHandler.LoadCell`
и `Players[pid]:LoadCell()` (`os.clock()` вокруг вызова или время из лога) на
самой большой клетке (`world/cell/-3, -2.json`), затем повторить с загруженным
`cjson`. Критерий: разница в пределах погрешности — оставить как есть; десятки
миллисекунд и больше на переход — делать вариант со сборкой.

**Решение, если браться.** Только сборка `lua-cjson` под встроенный LuaJIT в
`bootstrap.sh` плюс проверка в `ops doctor` («модуль есть / модуля нет»).
Патч `jsonInterface.lua` и «положить .so руками» — не решение.

</details>

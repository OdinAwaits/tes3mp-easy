# P03 — Ops-клиент и маппинг ошибок

- Сделано: `internal/panel/ops.go` с `Ops`-интерфейсом из `05-panel.md` §7 и production-клиентом `OpsClient`.
- Production argv фиксирован: `sudo -n -u tes3mp /opt/tes3mp-easy/bin/tes3mp-easy-ops --root <root> --json <command> [args...]`; shell не используется, `Direct`/`NewDirectOpsClient` — только для тестов и локального запуска.
- `stdout` — ровно один JSON-envelope; второй объект, мусор, пустой ответ или отсутствие `data` дают `internal`. `stderr` пишется в logger, лимиты 1 MiB/64 KiB защищают 64 MiB cgroup.
- Таймауты: чтение 5 с, короткие мутации 2 мин, `backups create`/`mods import`/`mods deploy`/`state deploy` 10 мин. Мутации после таймаута не повторяются.
- `OpsError` хранит exit code, `error.code`, `message`, `details`; HTTP строится по exit code: 1→500, 2/8→400, 3→404, 4→409, 5→507, 6/10→503, 7/9→422, неизвестный→500. Exit code авторитетнее envelope. `OpsHTTPStatus`/`OpsHTTPStatusForCode` доступны обработчикам.
- `doctor` — исключение контракта: при exit 10 клиент сохраняет `data` и возвращает отчёт вместе с `checks_failed`/503.
- Типизированы `Status`, `Backups`/`BackupItem`, `Backup`, `ImportResult`, `DeployResult`, `Doctor`; `ConfigGet` отдаёт `values`, дополнительный `ConfigSnapshot` — ещё и `read_only`.
- Проверено: `go test -count=1 ./...`, `go test -race -count=1 ./internal/panel`, `go vet ./...`, `go build ./...`, `gofmt -l cmd internal`, `git diff --check`. Тесты покрывают всю таблицу exit codes, точный argv всех методов, sudo, успешные `data`, битые envelope, таймаут/отмену, лимиты вывода, отсутствие shell, `checks_failed` и реальный `execOpsRunner`.
- Ручной smoke настоящего `tes3mp-easy-ops` на пустом temp-root: `status` → `service_unavailable`/503, `backups list` → пустой список/200.
- Ограничение: маршруты ещё не используют клиент (P04–P05); `start`/`stop`/`restart` в ops пока не реализованы, поэтому сквозной сценарий появится позже.

## 2. Коротко о целевой картине

1. **Нативный запуск на systemd.** `tes3mp.service`, `tes3mp-panel.service` и
   `tes3mp-easy-backup.timer`; без контейнерного рантайма и файлов оркестрации.
2. **Управление через HTTPS-панель.** SSH нужен для установки и аварийного
   восстановления, а не для повседневной работы.
3. **Бэкапы — каждые 5 минут.** State и моды публичны для скачивания;
   месячные архивы хранятся навсегда, пока хватает диска.
4. **Один административный писатель.** Административные изменения в `configs/`,
   `players/`, `world/`, `mods/` и `backups/` вносит только `ops`; сам
   `tes3mp.service` пишет `players/` и `world/` во время игры. Панель читает и
   вызывает ops от `tes3mp` через узкое sudo-правило.
5. **Клиент — простой и кроссплатформенный.** Windows 10/11 и Linux через
   Proton, один бинарник, мастер без терминала.

## 3. Принятые решения

| Решение | Почему | Где детали |
|---|---|---|
| Серверная обвязка (ops/panel) и клиент на Go | Один язык, статические бинарники, тестируемость | 02, 04, 05, 06 |
| Запуск через systemd, без контейнерного рантайма | ~80 MiB меньше фоновой памяти и узкая модель привилегий; Docker влезает, но оставляет меньше запаса | 02, 08 |
| Ops — отдельный CLI, панель вызывает подпроцессом | Один писатель, аварийный доступ, стабильный JSON | 04 |
| `tes3mp` и `tes3mp-panel` — разные пользователи | Игра не получает доступ к паролю, панель — к записи мира | 02 |
| Sudo только на ops и фиксированный rootctl | Панель не root, ops не получает произвольный shell | 02 |
| HTTPS по IP, Let’s Encrypt, без домена | Не требовать DNS от домашнего сервера | 05 |
| Один админ и один пароль, Argon2id 32 MiB/1 поток | MVP для одного человека и бюджет 64 MiB | 05 |
| Публичные бэкапы и текущий архив модов | Переносимость данных — цель проекта | 01, 05 |
| State и моды только в новых форматах | Один формат, проще валидация и тесты | 03 |
| Retention: 5 минут, дни, недели, месяцы навсегда | Долгая история без ручного труда | 03, 04 |
| Клиент на Fyne, логика отдельно от UI | Кроссплатформенность и тесты без окна | 06 |
| Никакой миграции старых конфигов и архивов | Чистая установка проще и безопаснее | 01, 03 |

## 4. Ветки и порядок работ

Основная ветка — `master`. Работа идёт в интеграционной `v2`, от неё создаются
ветки подсистем, от подсистем — ветки задач.

```text
master
└── v2
    ├── v2-docs
    ├── v2-infra
    ├── v2-ops
    │   ├── v2-ops-contracts
    │   ├── v2-ops-read
    │   └── v2-ops-mutations
    ├── v2-panel
    │   └── v2-panel-auth
    └── v2-client
        └── v2-client-installer
```

Важно: в Git нельзя одновременно иметь `v2/ops` и `v2/ops/contracts` — это
конфликт refs. Поэтому имена плоские: `v2-ops`, `v2-ops-contracts`.

Правила:

- `master` защищена; изменения только через merge из `v2` на milestone.
- `v2` — интеграционная ветка, всегда собирается и проходит тесты.
- Ветка подсистемы создаётся, когда начинается параллельная работа. Если работа
  идёт последовательно, задача может ветвиться прямо от `v2`.
- Задача живёт 1–3 дня, затем PR в подсистему, подсистема — в `v2`.
- Milestone-теги: `v2-m0-docs`, `v2-m1-infra`, `v2-m2-ops-read`,
  `v2-m3-ops-write`, `v2-m4-panel`, `v2-m5-client`, `v2-m6-packaging`.
- Контракты и фикстуры — foundation-шаг без отдельного milestone-тега:
  результат вливается в `v2` до `v2-m1-infra`.

Порядок из `02-architecture.md` §10:

1. Контракты и фикстуры.
2. Инфраструктура: bootstrap, systemd, пользователи, rootctl.
3. Ops только чтение.
4. Ops мутации и retention.
5. Панель MVP.
6. Клиент MVP.
7. Упаковка и E2E.

Детальная декомпозиция, статусы и acceptance-критерии — в
[`09-plan.md`](09-plan.md).

## 5. Правила ведения документации

- Документ без статуса и даты считается черновиком.
- Контракты (JSON, коды, форматы, API) живут только в `03-contracts.md`.
  Остальные документы ссылаются на разделы, а не копируют схемы.
- Меняешь контракт — меняешь фикстуры и тесты в том же PR.
- `docs/reference/` — справочники по TES3MP, а не описание нашей архитектуры.
- Старые гайды не поддерживаются и не лежат в `docs/v2/`.

## 6. Справочники

- `docs/reference/modding.md` — ограничения TES3MP 0.8.1, актуальны.
- `docs/reference/tes3mp-settings.md` — reference по `config.lua`, актуален.

## 7. Что считается готовым

Документация готова к реализации, когда:

- у каждой команды ops есть JSON-форма и код ошибки в `03-contracts.md`;
- у каждого публичного HTTP-маршрута есть схема ответа и поведение при ошибке;
- форматы `mods` и `state` описаны один раз и совпадают с фикстурами;
- retention и бюджеты описаны один раз: 5 минут, дни, недели, месяцы навсегда,
  1 GiB state, 512 MiB mods, резерв 512 MiB;
- в `07-testing.md` есть проверка на каждый контракт, retention и failure mode;
- в `08-runbook.md` есть действия для потери пароля, битого архива, нехватки
  места, недоступного systemd и сломанного TLS.

После этого можно начинать `v2-ops-contracts` и `v2-ops-read`.
